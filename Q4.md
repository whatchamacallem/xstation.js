# Q4: questions on R4.md, ranked by potential rework

Each question names the decision R4.md could not make without the
maintainer, the rework a different answer would cause, and what R4.md
assumes until told otherwise. Highest rework first. None restates a
decision already given; thirty-two is the cap.

## 1 Reload on failure against Project Direction 1.3

1.1 Q2.12 and Q2.20 make a full page reload the tested recovery path
and the reload on desync a requirement. The rules' Project Direction
1.3 says never retry by reloading the page, written for the old
bootstrapper's test. Rework if the rule stands: 4.5, 6.8, stage 6 and
the error handler change to an in-page recovery that recreates the
worker and reconciles. R4 assumes the rule sentence is the maintainer's
to amend and that reload stands.

## 2 Documents as KV rows

2.1 R4 6.4 stores a document as the KV row keyed `$id/$version` in
database `$db`, with `doc_put`, `doc_head` and `doc_get` as sugar over
`kv_*`, and no document table; `doc_head` is a prefix scan for the
highest version. Rework if a document table is wanted instead: the
substrate API, the SQL, two tools and replication. R4 assumes KV rows,
as Q1.14 described.

## 3 What "the only fixed schema" covers

3.1 Q2.21 makes the metaverse's universe table the only fixed schema.
R4 6.2 also puts the engine's `meta`, `kv` and `kv_gone` tables in every
database the substrate opens, so Document-Refs resolve anywhere and
blobs can be stored in a named database, and R4 6.6 seeds `world` and
`region` tables of mutable schema in each universe. Rework if the KV
tables may exist only in the engine databases: Document-Refs into AI
databases, the reference table prefetch and the media tiers change. R4
assumes the KV tables are the substrate, not experience schema.

## 4 The sleep API of the task manager

4.1 R4 4.2 has a handler return `task_sleep(state, wait_ids,
then_type)`; the queue enqueues `then_type` with `state` and the
replies once every awaited reply has arrived; one transaction per
dispatch, so a sleeping task holds no database. HTTP is a port that
answers `http.request` lines. Rework if the shape differs: every
handler that waits, the agent chain of 5.3, the permit flow and the
queue log. R4 assumes this shape.

## 5 Replication as forwarded operations

5.1 R4 6.8 forwards each committed `kv_put`, `kv_delete` and modifying
`sql_run` to the server as the same line, one way during play, with no
server push to an open tab, and replaces a differing file at start.
Rework if row level replication of the AI's tables, or a server push,
is wanted: the substrate on both sides, the line catalogue and stage 7.
R4 assumes operation forwarding, as Q2.20 describes a deterministic
replay.

## 6 Two threads

6.1 R4 merges the AI and WASM threads: sqlite3.wasm with the OPFS SAH
pool VFS in the AI worker, as Q2.6 asks if possible, and it is possible
in any dedicated worker. The three thread design goal sentence of Q1.3.2
is retired. Rework if three threads must stay: the substrate proxy,
the ai-wasm lane and its line types return. R4 assumes two.

## 7 The console tty mechanism

7.1 R4 2.3 serves the console through ttyd's `--url-arg`: a connection
with `?arg=console` runs `bootstrap.py ... console`, which in debug mode
execs dash through `verbose.call` and otherwise exits 1. The AI worker
owns that socket and relays it to the UI's xterm.js. Rework if ttyd
should instead run two commands, or the UI should own the socket: the
start script, bootstrap.py's role handling and the console lane. R4
assumes `--url-arg`, the one ttyd mechanism that varies the command per
connection.

## 8 The settings pipeline

8.1 R4 2.4 builds `settings.ts` from settings.json at build time, deep
frozen outside debug mode, and loads the same file into `_settings` on
the server, so `debug` is one key read by both. A `settings.put` takes
effect on the server at the next `hello` and in the page at the next
build. Rework if the page must receive settings in `hello` instead:
`settings.ts`, `error_handler.ts` ordering and the build. R4 assumes
build time, which is what lets `settings.js` load before anything
connects.

## 9 The representation of turns

9.1 R4 6.6 makes each turn a document `turn/<scene ref>/<n>`. The
alternative makes a scene's conversation the version history of one
document `turn/<scene ref>`, turn n being version n, which fits "each
scene is a new conversation" and costs `kv_delete` of versions on
compaction. Rework: `turn_append`, `turn_list`, `turn_compact` and
their tests. R4 assumes one document per turn.

## 10 Script run and debug

10.1 R4 5.6 runs a script with `new Function` in the AI worker against
the substrate's frozen API, returns the value or exception and the
verbose lines, and `script_debug` is the same run traced at level 2.
Q2.23 rejected HYPE-2's framing; what it requires of "run and debug
controls" beyond this is not stated. Rework if stepping or breakpoints
are meant: a script interpreter or DevTools in the loop. R4 assumes run
and trace.

## 11 The UI's part in the first replication test

11.1 Q2.2 replicates a string to string table "from the AI worker and
the UI". The UI has no SQLite (Q1.3.1). R4 8.7.7 submits the
modifications from the UI thread as tasks, forwarded to the AI worker's
database and then to the server. Rework if the UI must hold a table of
its own: a UI side substrate. R4 assumes modifications originate in the
UI.

## 12 The reference table in a document

12.1 R4 6.4 reads Q2.10 as: top level integer keys hold reference
strings, `{"$ref": n}` anywhere in the body names one, equal strings
share an entry, and the round trip is identical. Not stated: whether
`$ref` is the key name, whether a reference may appear inside a nested
document's own table, and whether media keys and Document-Refs share
the table. Rework: `doc_encode`, `doc_decode`, the prefetch. R4 assumes
`$ref`, one table per document, both kinds in it.

## 13 The DevTools driver

13.1 R4 8.2 specifies `devtools.py` by its API. The relay inside
`xsjs_screenshot.py` exists and HYPE chose it because it existed, which
the rules now name as the wrong reason. Rework either way is one
module. R4 asks: is the existing relay the implementation of that API,
or is `devtools.py` written fresh to it?

## 14 The debug tag and the overlay

14.1 R3 writes `<module "n"=3>` once and `<blob "n"=2>` once. R4 3.11
takes `<blob "n"=K>` with K the blob header index. The overlay shows
the last `verbose_ring` lines of a tty in both directions. Not stated:
whether DATA/ adopts the tag in place of `<N blobs>`, and whether the
ui-ai lane gets an overlay too. Rework: the renderer and the generator.
R4 assumes the tag, DATA/ adopts it, ttys only.

## 15 The last line regression test

15.1 Project Direction 1.1 keeps the test that keys on the last line of
a process exiting right after printing it. Under JSLB in raw mode the
server never exits right after output except on `error`. R4 8.7.3 keeps
the rung as it is against the old behaviour. Rework: none now; the rung
becomes meaningless when the old bootstrapper goes. R4 asks whether the
rung becomes "the `error` line before exit 1 arrives whole".

## 16 The verbose API

16.1 R4 7.2 names `verbose.log`, `dump`, `history_get`, `follow_add`
and `call`, the database `_verbose`, and the lines `verbose.put`,
`verbose.line`, `verbose.follow`, `verbose.tail`, `verbose.level`.
Q2.30 names only `verbose.log()`. Rework: renames across the catalogue.
R4 assumes these names.

## 17 The permit set

17.1 R4 marks `console_run`, `source_put` and `system_restart` as
permit tools. `sql_run` on server databases and `script_put` are not.
Rework: tool metadata and the stub conversations. R4 assumes those
three.

## 18 The provider key

18.1 R4 reads `XSJS_PROVIDER_KEY` from the ttyd process's environment
and sends it in `hello` (Q2.5, Q2.25). Rework: the start script sets
the variable; the name is a choice. R4 asks for the name and whether
the Windows start script should pass it through from the user's
environment.

## 19 Image URLs

19.1 R4 5.7 keeps `media.fetch` for a provider that answers a URL, from
the plan's "the AI worker loads media by sending URLs", beside the
`b64_json` first form of Q2.17. Rework if v0 is `b64_json` only: one
line type and one UI handler fewer. R4 keeps both.

## 20 The seeds

20.1 R4 6.6 seeds `hyperposition/1` and `prompt/analyst/1` in the
metaverse from repository files when the server creates the metaverse.
Not stated: where the files live and their format. R4 assumes
`python/seed/<id>.json`, the document in its encoded form.

## 21 Preferences in v0

21.1 `_preferences` exists by Q2.22 and Always Allow is tab only by
Q2.16, so nothing writes it yet. Rework: none. R4 asks whether v0 has
any preference, or the database exists empty with its schema.

## 22 The current player

22.1 R4 6.6 keeps the player in use as `current` in the metaverse's
`meta` table and the universe row as `(name, title, player, world)`.
Rework: the one fixed table and `player_switch`. R4 asks whether a
player table is wanted instead, which would be a second fixed schema.

## 23 "MVC" in Q2.21

23.1 Q1.2.1 says this is not MVC; Q2.21 says the AI needs MVC to
implement the tables and the tests need stubs that use the MVC. R4 5.1
reads the second as the tool layer and the stubs. Rework: naming only.
R4 asks what the term names.

## 24 The TAP line

24.1 R4 8.1 sends each case as `tap.line {language, text}` and the
consumer returns plan, pass, fail, skip and well formed. Rework: the
consumer and the test page. R4 asks whether the per case line carries
the TAP text or a structured result.

## 25 The highlighted report

25.1 The plan asks for colour on HTML output with the whole failed line
highlighted; R4 8.1 keeps it in `test.html`. The rules ban unrequested
style. Rework: none. R4 asks that it stays requested.

## 26 Model names

26.1 Q2.4 names xAI and no models. API/settings.json holds `grok-4` and
`grok-2-image` as placeholders. Rework: none. R4 asks for the two names.

## 27 Database creation tools

27.1 Q2.21 lets the AI add and remove databases. R4 5.5 exposes
`universe_create`, `world_create` and `region_create`; `db_create` and
`db_drop` exist in the substrate and are not tools. Rework: two tools.
R4 asks whether the AI may create a database outside those three.

## 28 A page built from other settings

28.1 R4 2.4 has `hello` carry `settings_sha256` and the AI worker
refuse a server whose file differs from the page's build. Rework: one
check. R4 asks whether the refusal is wanted, or the server's values
win.

## 29 Wire traffic in the server's verbose

29.1 R4 2.6 forwards the rendered wire traffic to `_verbose` in debug
mode. A 128 MiB upload renders as one line, but a turn is many. Rework:
a level or a setting. R4 assumes level 2 and `verbose_forward` gating.

## 30 The console lane's owner

30.1 R4 4.7 routes every console keystroke UI to AI to tty 0 and back,
so the AI worker is the only owner of sockets. Rework if the UI thread
may own tty 0: one socket moves and `console_run` relays the other way.
R4 assumes the AI worker.

## 31 The xterm.js fallback

31.1 R4 2.6 keeps "the headless package is the fallback for feeding"
from Q1.4.2. The rules ban fallbacks in code; this is a design
alternative chosen once by the research result. Rework: none. R4 asks
that the word is read that way.

## 32 Reserved tty numbers

32.1 R4 2.1 reserves ttys 2 and up for players (10.1) and makes the
role in `--url-arg` the tty number. Rework: none now. R4 asks whether
the role names are `console`, none, and `player2` onward.
