# R4: the hyperposition-engine plan, third pass

This replaces HYPE-2.md. It applies the thirty-two answers of 2026-10-18
in HYPE-QUESTIONS-2.md ("Q2.n"), the answers of R3.md to the audit in
tmp/Q3.md ("R3 n"), and keeps the thirty answers of HYPE-QUESTIONS.md
("Q1.n") and the draft hyperposition-plan.md ("plan"). Where this
document and HYPE-2.md differ, this one stands. Open decisions are in
Q4.md and referenced as Q4.n. API/ and DATA/ predate this pass and are

Every element below names the request that motivates it. Section 10

that no engineering log needs rereading.

## 1 Method

### 1.1 APIs before code

- An incomplete code base with correct APIs is worth more than a demo
  rewritten later (Q1.2.3). Every protocol is emulated as the real
  protocol from the first line: MCP is JSON-RPC 2.0; the provider is
  spoken to in the chat completion shape; TAP is TAP.
- Order of work: design the module here and in API/, write its test
  module, write the module, fix it, stack the next module on it with
  calls going one way, down (plan, Code quality). No module calls up or
  sideways.
- Documents iterate until the APIs are right. A stage that would need an
  API rewritten later is not started. "Stop designing things and start
  building the APIs I need from the bottom up" (R3 2.5): nothing here is
  a prototype or a draft; each stage is the final module behind its API.

### 1.2 Fail fast

- No error is swallowed, defaulted or retried (Q1.7.2, rules). A failed
  server handler writes one `error` line and exits 1 (Q1.7.1). In the
  page, `error_handler.js` replaces the screen with the message and the
  call stack in a `<pre>` and stops the app (Q2.24). Recovery is a full
  page reload, the tested path (Q2.12, Q2.20; Q4.1).

### 1.3 One synchronization tool

- The task manager is the only synchronization tool (Q1.20). A handler
  is synchronous. A handler that must wait returns a sleep to the task
  manager, which wakes it with the replies as a new task (Q2.7, R3 2.4).
  No promise, lock, shared buffer or `Atomics` exists outside the task
  manager and the ports it owns; the check in 8.6 audits for them.

### 1.4 Encode and decode before use

- JSLB's encoder and decoder are proven, in both languages, against the
  vectors of 8.3, before the format carries anything (R3 1.3). Stage 1
  is that proof and nothing else.

### 1.5 Nothing unmotivated

- Nothing concrete exists ahead of the prose that describes it. A
  module, line type, table, tool or setting appears here only with its
  request. Existing code in the checkout is current state, not design:
  the bootstrapper, its page, the screenshot tool and the wire test are
  reused only where this plan chooses them (Q1.10, rules), and the
  choice is stated where it is made (8.2, Q4.13).

### 1.6 What the third pass changed

1.6.1 Two threads, not three: UI and AI. sqlite3.wasm and OPFS run in
the AI worker, which owns every database (Q1.3.2, Q2.6, R3 2.3).

1.6.2 Two ttys, not one: the engine tty is Python speaking JSLB in raw
mode; the console tty is ttyd's own dash under xterm.js, optional and
debug only (plan, Q1.6, Q2.27, R3 2.1).

1.6.3 The task manager wakes sleeping tasks; handlers never hold a
promise (Q2.7, R3 2.4). Forwarding is a decoded object passed unchanged
from the receiving port to the sending port (R3 1.3).

1.6.4 `verbose` is the one logging, telemetry and dump namespace; the
`log` namespace is gone (Q2.30, R3 1.1). `verbose` is also where the
one external call, the console's dash, goes through (R3 2.2).

1.6.5 A Document-Ref is `/$db/$id/$version` or `$id/$version`; `$id`
may hold path separators; a document is a KV row (Q2.3, R3 2.5, Q4.2).
A document's references are an integer-keyed table in the document
(Q2.10).

1.6.6 Replication forwards every modifying substrate operation to the
server as it commits; at start the browser's copy is replaced when it
differs; desync reloads (Q2.2, Q2.20).

1.6.7 Engine databases carry a leading underscore: `_settings`,
`_files`, `_preferences`, `_verbose` (Q2.22). The metaverse's universe
table is the one fixed experience schema; worlds and regions are tables
the AI may alter (Q2.21).

1.6.8 Settings are built into `settings.js` from settings.json, deep
frozen outside debug mode; debug mode is a setting; `error_handler.js`
loads first (Q2.18, Q2.24, Q2.26).

1.6.9 The AI edits, runs and debugs its scripts live in the browser
over MCP; they are cached and backed up by replication (plan, Q2.23).

1.6.10 Tests are unittest in both languages with the project's own
`tap.producer` and `tap.consumer`; each browser test case travels to the
server as its own line (Q2.13, Q2.14).

1.6.11 The provider key comes from the environment, never a file in the
checkout (Q2.5). Images come back as `b64_json` test patterns in the
tests (Q2.17).

1.6.12 bootstrap.py can receive a new main loop from the page and serve
it after restart, in debug mode only (Q2.32).

1.6.13 Debug overlays: ctrl-0 toggles the console's xterm.js; ctrl-1 to
ctrl-n show the JSON part of recent JSLB on tty n (Q2.15, R3 1.2, 2.1).

1.6.14 No version floors or checks (Q2.31). Node runs tsc at build time
only (Q2.1).

## 2 Architecture

### 2.1 Processes, threads and ttys

```text
browser tab
  UI  main thread   error_handler, settings, page: DOM, input, media_db,
                    console view (xterm.js), overlays, permission
  AI  worker        every database (sqlite3.wasm on OPFS); wire; task
                    manager; agent; MCP; scripts; provider over HTTPS
       |                 |
       | tty 1: JSLB     | tty 0: ttyd's own protocol, debug only
       v                 v
ttyd --url-arg, one per machine, one program per WebSocket
  python3 bootstrap.py --root ~/.cache/xsjs           (tty 1, raw mode)
  python3 bootstrap.py --root ~/.cache/xsjs console   (tty 0: exec dash)
     |
     v  SQLite files under the root
  _settings _files _preferences _verbose metaverse <universe> ...
```

- One Python process per engine connection, no threads, no asyncio: a
  `select` loop on the pty (plan: bootstrap.py runs main_loop.py).
- The front end is TypeScript, the back end Python; the division is
  permanent (plan). SH appears in admin scripts and in the console tty
  only. Neither SH nor Python is exposed to a socket except through the
  JSLB dispatcher's single door, which is the part of the security
  architecture enforced now (R3 2.2); the console tty is the one
  exception, optional and debug only (Q2.27).
- Further ttys are Python, never dash (plan). ttys are numbered: 0 is
  the console, 1 the engine, 2 and up are reserved (10.1).

### 2.2 The two threads

- UI: builds the DOM once, routes the player's text and clicks to the AI
  worker as tasks, paints what `render` names, keeps `media_db`, a
  JavaScript map from media key to decoded image under a byte budget
  (Q1.3.1), hosts the console view and the overlays, shows permission
  requests, and runs `error_handler`. It owns no SQLite and never sees a
  wire.
- AI: owns both WebSockets, the task manager's owner table, sqlite3.wasm
  with the OPFS SAH pool VFS, every database and the cache directory
  (Q1.3.2, R3 2.3). It runs the agent (5.3), the MCP server and client
  (5.4), the AI's scripts (5.6) and replication (6.8). A long query
  stalls the agent, which is accepted: the provider's latency is larger,
  and the AI can raise the verbose level and optimize (R3 2.3).
- A third thread, if a hard need arises, reuses `queue.ts` and
  `substrate.ts` unchanged with a new owner table entry (Q1.2.1).

### 2.3 The ttys

- ttyd runs with `--url-arg`. Its command is `python3 bootstrap.py
  --root <root>`; a connection to `/ws?arg=console` appends `console`.
- tty 1, the engine: bootstrap.py with no role puts its pty in raw mode
  (Q1.8.1) and speaks JSLB. The AI worker opens it at page load.
- tty 0, the console: bootstrap.py with role `console` in debug mode
  execs `/bin/dash` through `verbose.call` with a scrubbed environment
  and the root as working directory (R3 2.2); outside debug mode it
  exits 1 and ttyd closes the connection. Its pty stays cooked, so it
  echoes. The page's console module speaks ttyd's own client protocol
  to it, which is ttyd's dash and xterm.js recycled (plan). The user
  opens it with ctrl-0 or the AI opens it with permission (Q1.15,
  Q1.11.2). No log-in beyond ttyd's own (Q1.15).
- Sandboxing the dash is a door (10.4).

### 2.4 Settings, debug mode and the error handler

- `settings.json` at the checkout's top level holds every constant with
  a sane default (Q1.27, Q2.18): see 6.9. Start copies it to the root.
- `page_build.py` generates `settings.ts` from it, so the page carries
  the same values the server reads, unmodified (Q1.27). `settings_get
  (id)` is an id based lookup. Outside debug mode the object is deep
  frozen; in debug mode `settings_set(id, value)` changes the live value
  and `settings.put` writes the file in the root (Q2.24).
- Debug mode is the setting `debug`, false in a release (Q2.26). The
  server reads the same file, so `hello` reports what the page already
  knows and refuses a page built from a different file (Q4.28).
- `error_handler.ts` compiles to the first script in the page. It
  catches `error`, `unhandledrejection` and resource load failures in
  the UI, and `fault` lines from the AI worker, and replaces the screen
  by `document.write` with a `<pre>` holding the message and call stack,
  then closes the wire and terminates the worker (Q2.24). `settings.ts`
  loads second; everything else after.
- Headers use full names in debug mode, short names otherwise (plan).

### 2.5 The page and its build

- ttyd serves one static file, `build/hyperposition-engine.html`
  (Q1.4.1). Changing it needs a rebuild and a reload. Nothing is fetched
  at run time but media URLs, when the provider returns one (5.7).
- `ts/` holds every script. tsc compiles them with `module` none and
  `outFile` into one classic script in reference order; each file
  defines one frozen object named after its module. Node runs tsc at
  build time and nothing else, ever (Q2.1).
- `page_build.py` merges `html/engine.html` and `html/engine.css`, the
  bundle, sqlite3.wasm as base64 and xterm.js into the one file; the AI
  worker is a Blob URL of the same bundle with its entry chosen by
  `self.name`. The output's SHA-256 is the page's version in `hello`.
- `html/test.html` is built the same way with the test modules added.
- Canonical TypeScript error handling: `strict` on, every thrown value
  an `Error` with `cause` when wrapped, no empty catch (Q1.4.1).
- The AI's scripts are not in the bundle: they are KV values the AI
  edits live (5.6). tsc precompiles only the modules the AI does not
  edit (Q2.23).

### 2.6 Debug overlays

- ctrl-0 toggles the console view: one xterm.js instance in a hidden
  container, shown with its scrollback, colours and features intact
  (Q1.4.2, Q2.15, R3 1.2). Research goal, kept: whether xterm.js can be
  fed while hidden and keep its state; the headless package is the
  fallback for feeding.
- ctrl-n, n from 1, toggles the overlay of tty n: a `<pre>` holding the
  JSON part of the last `verbose_ring` lines in both directions, newest
  last, each blob replaced by the debug tag `<blob "n"=K>` where K is the
  blob header's index (R3 1.2, 2.1; Q4.14). These overlays are read
  only and have no console features (Q2.15).
- In debug mode the same rendering is what `verbose.put` forwards to
  the server for the wire, so the server's `_verbose` holds the page's
  view of the traffic (Q1.4.1).

## 3 JSLB wire format

### 3.1 Framing

```text
message := line blob*
line    := json-object CR
```

- `json-object` is one JSON object in UTF-8 with no whitespace outside
  strings. The encoder emits no CR and JSON forbids a raw CR inside a
  string, so the first CR, byte 0x0D, ends the line (plan).
- LF is an ordinary byte with no meaning, as every byte other than CR
  outside a string (Q1.8.2).
- The blobs follow the CR at once, in header order, each exactly `s`
  bytes, nothing between (plan).
- A reader has two states: bytes to a CR, then known byte counts.

### 3.2 Line header, key `"0"`

- `t` `type`: string, required (Q1.9.2). The handler name: lowercase
  words joined by `_`, namespaces by `.`.
- `v` `version`: integer, default 0 (Q1.9.2).
- `i` `id`: integer from 1, present when a reply is expected (Q1.9.1).
- `r` `reply`: integer, the peer's `i` this line answers (Q1.9.1).
- `k` `key`: string, the key the line is about, when it is about one.
- `b` `blobs`: integer, default 0.

### 3.3 Blob headers, keys `"1"` to `"b"`

- `s` `size`: integer, required. `k` `key`: where the handler stores
  the blob, when it does. `d` `data`: never serialized; in memory the
  bytes, or for a streamed blob the path of its cache file (3.7).
- Any other field is the handler's. There is no blob type registry: a
  blob is opaque bytes to JSLB and to the dispatcher (Q1.9.3).

### 3.4 Names and defaults

- Short names or full names in all headers of a line; both in one line
  is a hard error. Full names are the debug mode form (plan).
- A field at its default is not written (Q1.9.2).
- The payload is the set of keys that are not decimal integer strings;
  decimal integer keys are headers (Q1.1.1).
- The decoder returns headers as sent plus `d`; `field_get(header,
  "type")` resolves short or full name and the default.

### 3.5 Values

- Numbers are IEEE doubles; integers lie within plus or minus 2^53;
  the Python encoder refuses larger ints, NaN and infinities.
- Strings are Unicode; the line is UTF-8 under the strict decoder on
  both sides. Duplicate keys take the last value; encoders never produce
  them.

### 3.6 Hard errors

- No `"0"`, no `t`, `b` not matching the headers present, a gap in
  `"1"` to `"b"`, a non-integer or negative `s`, a payload key that is a
  decimal integer string, both name forms, an unknown field in the line
  header.
- A line over `line_max` or a blob over `blob_max`, refused before the
  bytes are buffered.
- The decoder raises on the first error and the port that fed it
  closes. No resynchronization on a byte stream.

### 3.7 Streaming blobs

- A blob of `s` at most `overflow_bytes` is collected in memory. A
  larger blob is written to a new file in the cache directory as it
  arrives, hashed on the way, and `d` is that path; the handler moves
  or links it (Q1.12). Memory per connection is bounded by `line_max`
  plus `overflow_bytes`.
- The encoder yields the JSON bytes, then each `d` as is, bytes or
  file. It never copies blob bytes.

### 3.8 Request, reply, push

- A line with `i` gets exactly one line with `r` equal to it, from the
  peer, on the same port; its `t` is the request's `t` or `error`. A
  line without `i` is a notification (Q1.9.1).
- Ids restart at 1 per port per process lifetime. An unknown `r` is a
  hard error.
- One port is one FIFO each way. A handler runs to completion before
  the next line on that port is dispatched (4.2).

### 3.9 Transport

- ttyd frames: `'0' + bytes` each way, `'1'` title and `'2'`
  preferences first. `wire.ts` strips and adds the `'0'`.
- The server puts its pty in raw mode with `tty.setraw` before writing
  anything (Q1.8.1). The client sends nothing until `hello` arrives.
- ttyd's 5 s ping is answered by the browser's network stack.

### 3.10 Flow control

- ttyd stops reading the pty after each 64 KiB read until it is written
  to the socket; client to pty input goes to libuv's unbounded write
  queue; the one option is `--srv-buf-size`, the receive chunk size.
- Decision (Q1.23, Q2.9): ttyd runs with `--srv-buf-size 1048576`;
  `chunk_bytes` is 1 MiB; `wire.ts` waits for `bufferedAmount` under
  one chunk before the next; the server streams big blobs to the cache
  file so libuv's queue stays short. ttyd's resident size during a
  128 MiB upload is measured in stage 2; a credit line is added only if
  the measurement demands it (10.11).

### 3.11 Debug rendering

- A line is rendered for a human as its JSON text followed by one
  `<blob "n"=K>` tag per blob, K the header index from 1 (R3 1.2,
  2.1). The overlays (2.6), `verbose.put` of wire traffic and the
  transcripts in DATA/ use this form (Q4.14).

## 4 Communication patterns

### 4.1 Lanes and ports

```text
wire     AI worker  <->  server        bytes over tty 1
console  AI worker  <->  ttyd's dash   ttyd's protocol over tty 0
ui-ai    UI thread  <->  AI worker     structured clone, buffers moved
mcp      agent      <->  MCP server    JSON-RPC objects, local port
http     agent      <->  provider      HTTPS, one request per line
```

- Every message on every lane is one JSLB object (plan: JSLB
  everywhere except the console). A port is anything with
  `line_post(line)` and `line_receive(fn)`: local, thread
  (`MessagePort`), wire, and http, which turns `http.request` into a
  `fetch` and posts the response as the reply line. The console lane
  carries ttyd's protocol bytes wrapped as `console.output` and
  `console.input` lines on the ui-ai lane, so that the AI worker is the
  only owner of sockets.
- Code that submits a task never knows which port carries it (plan).

### 4.2 The task manager

- `TaskQueue` per thread. It dispatches one line at a time; a handler
  runs to completion (Q2.7). The owner table maps a type prefix to the
  thread that handles it; a line whose owner is another thread is
  posted to that thread's port unchanged (4.3).
- A handler returns one of three things: a reply line, when the task
  had `i`; nothing, for a notification; or a sleep. A sleep names the
  ids of the requests the handler submitted and the type of the task to
  wake with: `task_sleep(state, wait_ids, then_type)`. When every reply
  in `wait_ids` has arrived the queue enqueues a line of `then_type`
  whose payload is `state` and the replies (Q2.7, R3 2.4). A task can
  therefore re-enqueue itself in a different form at a different
  destination any number of times.
- Locking: every database is on the AI thread and one task runs at a
  time, so a running task holds every database. A sleeping task holds
  nothing: `transaction_run` is the only way to touch a database and it
  cannot span a return, so the handler has committed before it sleeps.
  That is the task manager's locking scheme (Q2.7).
- The queue handles sleeping tasks and an empty queue. It logs every
  submit, dispatch, sleep, wake and reply through `verbose` at level 2,
  and no other information is needed to reconstruct the thread's
  timeline (Q2.7).
- Blob buffers are transferred, never copied; after submit the caller's
  `d` is detached (plan: owned data array).
- The audit of 8.6 fails the build on any `await`, `then(`, `new
  Promise` or `Atomics` outside `queue.ts`, `wire.ts` and `http.ts`
  (R3 2.4).

### 4.3 Forwarding

- A line arriving on one port whose owner is not this thread is passed
  as the decoded object, unchanged, to the port of its owner, which
  encodes it again (R3 1.3). The owner table on the AI thread maps
  `verbose.` to `server`, so a `verbose.put` from the UI reaches the
  server through the AI worker with nothing added; the plan's embedded
  forwarding instruction is the type itself. Explicit route headers are
  a door (10.10).

### 4.4 Connection lifecycle

- Open: `error_handler`, `settings`, then `page.ts` creates the AI
  worker from the bundle. The worker fetches `/token`, opens `/ws` with
  subprotocol `tty`, sends ttyd's first message, skips title and
  preferences, waits for `hello`.
- `hello` is the server's request with `i` 1: `bootstrap`, `sha256`,
  `pid`, `python`, `sqlite`, `root`, `settings_sha256`, `seq` per server
  database, `provider_key` (Q2.5, Q2.25). The worker answers with the
  page's `sha256`, a `tab` id and `seq` per browser database, then posts
  `boot.hello` to the UI.
- Then, as tasks: for each engine database and the metaverse, compare
  `seq`; replace the browser's file from the server where they differ
  (6.8); read the current player, universe, world and scene; fetch the
  scene's referenced media the browser lacks; `render`.
- A second tab on the same root is refused by the second tab (Q2.11).
- Close: the worker closes the WebSocket with 1000; ttyd sends SIGHUP
  and the server exits. There is no `quit` and no `cancel`; a runaway is
  ended by closing (Q1.8.1).

### 4.5 Errors and recovery

- Server: a handler that raises produces one `error` line with `r` when
  the request had `i`, `message` and `stack`, written and flushed
  before exit 1; the realistic effort to get the message out (Q1.7.1).
- Page: any fault reaches `error_handler`, which shows it and stops the
  app (2.4). The screen offers Reload. Reload is `location.reload()`;
  the new page replicates from the server, which is the source of
  truth (Q2.12, Q2.20). Nothing in flight is retried. This contradicts
  the rules' Project Direction 1.3 as written (Q4.1).
- Desync (6.8) is a fault like any other and ends in Reload.

### 4.6 Permission

- A tool marked `permit` is not run until the UI shows the request with
  Accept, Deny and Always Allow below it (Q1.11.2). Accept runs it once;
  Deny returns an error to the model; Always Allow lasts the tab and is
  not stored (Q2.16).
- Two tasks: `permit.ask` from AI to UI returns at once with the request
  shown; `permit.answer` from UI to AI carries the choice and wakes the
  sleeping tool call.

### 4.7 The console lane

- `console.open` from the UI makes the AI worker open tty 0 and relay:
  output arrives as `console.output` with one blob, input goes as
  `console.input` with one blob, `console.close` closes the socket,
  `console.exit` is pushed when ttyd closes it. The server side is ttyd
  and dash; no Python line type exists for the console.
- The AI reaches it only through the `console_run` tool after the
  permission flow (plan: AI has MCP access to dash; may have to ask).

## 5 The AI

### 5.1 Not MVC

- The model of this system is the set of databases on one thread.
  Threads that talk directly and keep private storage, `media_db` for
  one, are part of the design (Q1.2.1). The phrase "the AI needs MVC"
  in Q2.21 is read as the tool layer of 5.5 and the stubs of 8.5; Q4.23
  asks.

### 5.2 The generic provider protocol

- The chat completion protocol: `POST {base_url}/chat/completions` with
  `model`, `messages`, `tools`, `tool_choice`; `choices[0].message` with
  `content`, `tool_calls` and `finish_reason`. Images: `POST
  {base_url}/images/generations` with `response_format` `b64_json`
  (Q2.17). xAI is the first and only provider tested; the same shape
  for others is a door (Q2.4, 10.6).
- `provider.ts` is the one door: `chat_request(messages, tools)` and
  `image_request(prompt)` each build one `http.request` line with the
  key in `Authorization`; the caller submits it and sleeps. The key is
  read by the server from the environment variable `XSJS_PROVIDER_KEY`
  and sent in `hello`; it lives in the AI worker's memory only (Q2.5,
  Q2.25; Q4.18).
- `provider_script.ts` answers the same lines with no network: a script
  is a table of nodes; the player's message is one integer that selects
  the node's reply, which may carry tool calls; a tool result advances
  to the node the reply names. Image requests return a low resolution
  PNG test pattern with hard pixel edges drawn by the stub (Q1.2.2,
  Q2.17, Q2.21). Every automated test drives the engine this way; no
  AI runs in tests.

### 5.3 The agent loop

- One turn is a chain of tasks. `ai.say {text}` or `ai.click {x, y}`
  from the UI: the handler appends the turn (6.6), builds the provider
  request, submits it and sleeps with `ai.model_reply`. `ai.model_reply`:
  stores the assistant turn; for each tool call runs MCP `tools/call`;
  a tool that must wait (an image, a permit) submits and sleeps with
  `ai.tool_reply`; when every tool result is in, the next provider
  request is submitted; a reply with no tool calls ends the turn with
  `render` to the UI and the reply to the original `ai.say`. The queue
  log is the transcript of the turn (4.2).
- The system prompt is the analyst's prompt document in the metaverse,
  then the current universe's prompt document (plan).
- Time stops: nothing runs without a player task; the agent sets no
  timers (plan).

### 5.4 MCP

- `mcp.ts` and `mcp.py` implement JSON-RPC 2.0 and the MCP methods
  `initialize`, `notifications/initialized`, `ping`, `tools/list` and
  `tools/call`, revision `2025-06-18` pinned, any further part of it
  emulated when a tool needs it (Q1.2.3, Q2.8). Both are transport
  agnostic: `message_handle(object)` returns the response or nothing.
- Transports: a local port in the AI worker; the JSLB line `mcp` whose
  payload is the JSON-RPC message; `mcp_stdio.py`, newline delimited on
  stdin and stdout, so an external agent drives a server directly.
- The client sees browser tools and server tools in one flat list
  under `browser.` and `server.` prefixes.

### 5.5 Tools

Browser, in the AI worker; each names its request:

- `sql_run {db, statements}`: the single door to SQL; DDL allowed, the
  AI is the database administrator (Q1.18, Q2.19). Engine databases
  refuse schema changes; `_settings` refuses writes (Q2.22).
- `kv_get`, `kv_put`, `kv_list`, `kv_delete` (plan: KV accessor).

## 6 Data

### 6.1 Engines and connections

- Server: Python's `sqlite3` on the system library. Browser:
  sqlite3.wasm pinned by version and SHA-256 with the OPFS SAH pool VFS
  in the AI worker. No version floors and no version checks (Q2.31).
- One connection per database. Server pragmas: `foreign_keys=ON`,
  `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`.
- A database name is a C identifier (Q2.21). Its file is
  `<name>.sqlite` under the root.

### 6.2 Databases

```text
name          holds                                       schema
_settings     settings.json loaded, string to JSON string  immutable
_preferences  the user's preferences, string to JSON       fixed
_files        media, scripts and blobs by key              fixed
_verbose      the server's verbose lines (server only)     fixed
metaverse     the universe table; player, analyst, turns   universe fixed
<universe>    world and region tables; the experience      AI's
```

- The three browser databases of the plan, settings, preferences and
  files, are these, on the AI thread (plan, Q1.3.2), named with a
  leading underscore (Q2.22). `_settings` is immutable; `_preferences`
  and `_files` have an immutable schema (Q2.22).
- Every database opened by the substrate holds the KV table of 6.3,
  which is how a Document-Ref resolves in any database and how blobs
  are stored in a given database (plan). The metaverse adds the
  `universe` table, the one fixed experience schema (Q2.21; Q4.3).
- The AI creates and drops databases and tables as the experience needs
  (Q1.18, Q2.21).

### 6.3 The KV table

```sql
CREATE TABLE meta (
    name  TEXT PRIMARY KEY,
    value TEXT NOT NULL
) WITHOUT ROWID, STRICT;

CREATE TABLE kv (
    key    TEXT    PRIMARY KEY,
    size   INTEGER NOT NULL,
    sha256 BLOB    NOT NULL,
    data   BLOB,
    seq    INTEGER NOT NULL UNIQUE
) WITHOUT ROWID, STRICT;

CREATE TABLE kv_gone (
    key TEXT    PRIMARY KEY,
    seq INTEGER NOT NULL UNIQUE
) WITHOUT ROWID, STRICT;
```

- `sha256` names the overflow file, detects an unchanged write, and
  lets replication skip bytes the other side has. `seq` comes from
  `meta` row `seq` in the same transaction. `kv_gone` records deletions
  so that they replicate. `data` is NULL when the value is in the cache
  (6.5). No type column: what a value is, is the key owner's business.

### 6.4 Documents and Document-Refs

- Grammar (Q2.3, R3 2.5): `/$db/$id/$version` is an external reference,
  `$id/$version` an internal one. `$db` is a C identifier, `$id` any
  non-empty UTF-8 text, which may contain `/`, `$version` an integer
  literal. The version is the last segment; nothing else about the
  shape of `$id` is fixed.
- A document is a KV row keyed `$id/$version` in database `$db` whose
  value is JSON (Q1.14: push new versions into the KV with the version
  on the key). `doc_put(db, id, body)` writes version head plus one;
  `doc_head(db, id)` is the highest version under prefix `$id/`;
  `doc_get(ref)` is `kv_get`. A written version never changes; history
  is the set of versions. There is no document table (Q4.2).
- References inside a document (Q2.10): the top level integer keys
  `"0"`, `"1"`, ... hold reference strings, and `{"$ref": n}` anywhere
  in the body names one. `doc_encode(normal)` moves every reference
  string into the table and leaves `{"$ref": n}` behind, sharing equal
  strings; `doc_decode(encoded)` puts them back. The round trip is
  identical. The engine prefetches from the table without knowing the
  schema; `doc_get` of a reference the browser lacks asks the server
  with `kv.get` and stores the answer first.
- Pushing a new scene is `doc_put` of the scene and an update of the
  world's current scene (6.6). Replication carries both.

### 6.5 Overflow to the cache

- A KV value over `overflow_bytes`, 128 KiB (Q1.12), lives in
  `<root>/cache/<sha256 hex>` with `data` NULL; the browser's cache is
  an OPFS directory in the AI worker. File first, then the row; a crash
  between leaves an unreferenced file that `kv_check` removes. The
  streaming decoder's file is renamed into place, no second copy.

### 6.6 Universes, players, worlds, regions, scenes, turns

- `metaverse.universe(name TEXT PRIMARY KEY, title TEXT NOT NULL,
  player TEXT NOT NULL, world TEXT NOT NULL)` is the one fixed table:
  which player is in which universe and which of its worlds (Q2.19,
  Q2.21). Several players in several universes at once; `current` in
  the metaverse's `meta` names the player in use; by default there is
  one, `player` (Q2.19; Q4.22).
- A universe database is seeded with `world(name TEXT PRIMARY KEY,
  scene TEXT NOT NULL)` and `region(world TEXT NOT NULL, name TEXT NOT
  NULL, PRIMARY KEY (world, name))`, both of mutable schema: the AI
  alters, adds and drops as the experience needs; the seed goes no
  further (Q2.21). `world.scene` is the Document-Ref of the current
  scene (plan: the world holds a pointer to the scene).
- Defaults: `metaverse`, `current_universe` for simulations in the
  present day, `world` (Q2.21). The hyperposition is the scene document
  `hyperposition/1` in the metaverse, unmodifiable, and the analyst's
  prompt is `prompt/analyst/1` there; the server seeds both from the
  repository when it creates the metaverse (plan, Q2.20).
- Scenes are documents in the universe database; a region is disjoint
  entities, a scene a location inside it (Q1.17).
- Turns: documents `turn/<scene ref>/<n>` in the universe database, or
  the metaverse for the hyperposition, each one provider message.
  `turn_compact(scene)` in the substrate replaces turns 1 to N with one
  summary document when the estimate exceeds `turn_compact_tokens`; a
  heuristic baked into the wrapper, not an AI script (Q2.19; Q4.9).

### 6.7 Media tiers

media_db          UI thread   decoded images in use        by budget
_files (browser)  AI worker   the current region's refs    on leave
_files (server)   server      everything ever stored       never, v0

  Budgets are settings (Q2.18).

### 6.8 Replication

- Always over JSLB, as it happens, from the modifier to the server
  (Q2.2). The unit is the substrate operation: `kv_put`, `kv_delete`
  and every modifying `sql_run` commit in the browser is forwarded as
  the same line (`kv.put` with its blob, `kv.delete`, `sql.run`) to the
  server right after the transaction commits, in order, coalesced per
  database so one push is in flight. The server runs the same
  operation, so the copies are deterministic as long as the statements
  are (Q2.20). The server's reply carries its `seq`.
- This is inside the substrate, not ad hoc: `substrate.ts` emits the
  lines and `substrate.py` applies them (Q2.2). The first unit test
  replicates a string to string table, created and filled through
  `sql_run`, by modifications submitted from the UI thread and from the
  AI thread, and compares the server's copy (Q2.2; Q4.11).
- Direction: during play the browser writes and the server backs up;
  nothing is pushed from the server while a tab is open (Q2.20: one
  way). The server is the source of truth.
- Start: `hello` carries `seq` per database. Where the browser's `seq`
  differs, its file is invalidated and replaced by the server's:
  `db.snapshot` yields `Connection.serialize` bytes as one blob,
  `db.restore` writes a temp file and renames it (Q2.20).
- Desync: a push whose `since` is not the server's `seq` is refused
  with `error`; the page faults and reloads, and the reload replaces the
  file (Q2.20). That path is unit tested in stage 6, early. Content
  divergence with equal `seq` is a door (10.9).
- `_verbose` is server only. `_settings` replicates one way, from the
  file.

  `console_columns`, `console_rows`, `long_task_ms`, `port_windows`,
  `port_wsl`, `mcp_protocol_version`, `provider` with `scripted`,
  `base_url`, `chat_model`, `image_model`, `timeout_seconds`. Never a

  The Python main loop stays downloadable until then (Q2.32).

- Without root: environment scrub, working directory, resource limits,
  `os.unshare` for user and network namespaces; or a container. Any
  failure to apply one is a hard error. No line type changes.

10.5 Server side image fetching (Q2.17, a required door).

- `image.fetch {url, key}` to the server, which downloads the bytes
  with `urllib`, stores them in `_files` and replies with size and
  SHA-256; the browser then `kv.get`s them. Needed when a provider's
  image host refuses a browser origin.

10.6 Providers other than xAI (Q2.4).

10.7 Crossfade prefetch (plan, Terminology).

- When the world's scene changes, the next scene's reference table

  cross fades from the old image.

10.8 Switching the player in the page (Q2.19).

  a tool; a control in the page that offers it to the user is not
  built.

10.9 Content divergence detection (Q2.20).

- Equal `seq` with different contents, from a non deterministic
  statement: a per database checksum computed by the wrapper, the
  SHA-256 of every row in primary key order, compared at `hello` and
  after each push; a mismatch is a desync.

10.10 Explicit forwarding routes (plan, JSLB task queue module).

- A route list header each hop pops, for a line that must visit several
  threads with markup added at each, as the plan's diagnostics request
  example. The owner table covers the cases this plan needs (4.3).

10.11 A credit line for uploads (Q2.9).

  it.

10.12 The security audit (Q2.25, R3 2.2).

- The key in `hello`, the single door, the console tty, the permit set.

10.13 A sleeping task on the server (symmetry with 4.2).

- `dispatch.py` gains `task_sleep` and `main_loop.py` a wake table when

  provider door of 10.5 would.

10.14 Compaction beyond an estimate (Q2.19).

- A summary turn written by the provider rather than by truncation,

10.15 Line types versioned by handler (Q1.9.2).

- A handler registered per version; a line of another version is an
  error, not a translation; a breaking framing change is a new `hello`
  field. Nothing needs a second version yet.
